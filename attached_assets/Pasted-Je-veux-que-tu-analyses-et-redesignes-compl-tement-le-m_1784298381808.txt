Je veux que tu analyses et redesignes complètement le module Documents de mon application SaaS de gestion de syndicats et copropriétés.

Avant toute modification technique, je veux que tu comprennes le scénario métier complet.

=== SCÉNARIO GLOBAL ===

Le système contient plusieurs rôles :

1. Super Admin (éditeur de la plateforme)
2. Administrateur du Syndicat
3. Président du Syndicat
4. Trésorier
5. Secrétaire
6. Membre
7. Propriétaire
8. Locataire

Le Super Admin ne génère jamais de documents.

Son rôle est :

* gérer le catalogue des templates
* créer de nouveaux templates
* publier les templates
* gérer les versions
* gérer les workflows de signature
* gérer les demandes de nouveaux modèles

Le Super Admin agit comme un éditeur SaaS.

=== EXEMPLE 1 : AHMED DEMANDE UNE ATTESTATION ===

Ahmed est membre du Syndicat Résidence Atlas.

Ahmed ouvre l'application.

Il clique sur :

Documents
→ Nouvelle demande
→ Attestation d'adhésion

Le système ne doit PAS demander des informations déjà présentes dans la base.

Le système récupère automatiquement :

* nom complet
* email
* téléphone
* lot
* bâtiment
* résidence
* date d'adhésion
* statut de cotisation
* numéro membre
* syndicat
* adresse du syndicat

Ahmed ne saisit que les informations absentes de la base.

Le document est généré automatiquement.

=== EXEMPLE 2 : RAPPORT FINANCIER ===

Le trésorier veut générer un rapport financier.

Le système récupère automatiquement :

* budgets
* lignes budgétaires
* appels de fonds
* paiements
* caisse
* fonds de travaux
* impayés
* taux de recouvrement
* dépenses
* recettes

Aucune donnée financière ne doit être saisie manuellement si elle existe déjà dans la base.

=== EXEMPLE 3 : PROCÈS VERBAL ===

Le secrétaire termine une réunion.

Le système récupère automatiquement :

* réunion
* participants
* résolutions
* votes
* présence
* date
* lieu

Le PV est construit automatiquement.

=== EXEMPLE 4 : NOUVEAU TEMPLATE ===

Le Syndicat Atlas a besoin d'un nouveau document.

L'administrateur crée une demande.

La demande contient :

* titre
* description
* objectif
* champs nécessaires
* captures d'écran
* exemples PDF

Le Super Admin reçoit la demande.

Il crée le template.

Il publie une nouvelle version.

Tous les syndicats autorisés peuvent ensuite l'utiliser.

=== OBJECTIF DESIGN ===

Je ne veux pas des documents administratifs simples.

Je veux un niveau comparable à :

* DocuSign
* Adobe Sign
* SAP
* Oracle
* Microsoft Dynamics
* Odoo Enterprise

Chaque famille de documents doit avoir son identité visuelle propre.

Les attestations doivent ressembler à des certificats officiels.

Les rapports financiers doivent ressembler à des rapports ERP.

Les PV doivent ressembler à des documents de gouvernance.

Les contrats doivent ressembler à des documents juridiques professionnels.

=== PROBLÈMES ACTUELS ===

* couleurs incohérentes
* couleurs différentes de l'application mobile
* signatures réelles non visibles
* logos des syndicats non affichés
* header trop grand
* documents qui prennent 2 pages inutilement
* informations répétées
* beaucoup d'espace vide
* hiérarchie visuelle faible
* templates qui se ressemblent tous
* certains documents demandent des données déjà présentes dans la base

=== TA MISSION ===

1. Cartographier tous les templates.
2. Identifier les données disponibles dans la base.
3. Détecter automatiquement les informations récupérables.
4. Supprimer les saisies inutiles.
5. Reconcevoir chaque template individuellement.
6. Définir un Design System documentaire unique.
7. Proposer un workflow complet de génération, signature et validation.
8. Produire un plan détaillé Template par Template avec les données utilisées, les rôles impliqués et le design recommandé.

Ne commence pas à coder.

Commence par produire une analyse métier complète, un diagramme de flux utilisateur et une architecture documentaire cible.
